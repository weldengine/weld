## Contexte

M0.4 fait avancer le critère C0.3 (Renderer Vulkan forward minimal) en concevant la GAL (GPU Abstraction Layer) jour 1 pour accommoder Metal + D3D12 + WebGPU sans refactor Phase 2+, et en livrant un renderer Vulkan forward opérationnel par-dessus. La GAL est le point de bifurcation architecturale du moteur — figer sa surface publique maintenant évite un refactor 5-10× plus coûteux Phase 2. Le milestone absorbe en parallèle 6 dettes S2 sur le path Vulkan (PPM capture, dispatch bypass, whitelist closure, VkResult aliases, `*Raw` variants, suppression `vk_frame.zig` spike). C'est le **premier milestone d'application de la règle §4.5.1** (CI runtime sémantique obligatoire + validation manuelle GPU sur les 3 configs).

## Scope

- **GAL interface publique figée** dans `src/modules/render/gal/` — surface WebGPU-like (Device, Queue, CommandEncoder, RenderPassEncoder, ComputePassEncoder, BindGroup, BindGroupLayout, RenderPipeline, ComputePipeline, Buffer, Texture, TextureView, Sampler, Fence, Semaphore) avec escape hatches Phase 0 pré-câblés pour `TimelineSemaphore`, `BarrierExplicit`, `DescriptorIndexing` (types présents, fonctionnels minimaux Vulkan, no-op Null, utilisés Phase 1+). Auto-tracking des barriers par défaut, mode `BarrierExplicit` opt-in. Input pipeline = SPIR-V binaire uniquement (pas de source HLSL/WGSL).
- **Backend Vulkan** dans `src/modules/render/gal/vulkan/` — implémentation complète des concepts GAL Phase 0 (Buffer, Texture, Pipeline, RenderPass, swapchain, sync). Aucun accès direct à `vk.device_dispatch.*` depuis du code hors `gal/vulkan/`. Deux flags de sélection distincts : `--gpu-prefer=<discrete|integrated|index:N>` inchangé vs S2 (sélecteur hardware), nouveau `--vulkan-driver=<auto|hardware|software>` (sélecteur d'implémentation Vulkan : `auto` défaut = enum tous les devices et applique `--gpu-prefer`, `hardware` = filtre les devices `CPU` avant d'appliquer `--gpu-prefer`, `software` = force lavapipe ou équivalent et ignore `--gpu-prefer`).
- **Backend Null** dans `src/modules/render/gal/null/` — stubs no-op qui satisfont la vérification comptime de l'interface, utilisé en CI headless pour les tests de cohérence d'API.
- **Render graph minimal** dans `src/modules/render/render_graph/` — DAG déclaratif avec 3 passes Phase 0 : Depth prepass (D32_SFLOAT, pas de stencil) → Forward opaque (depth test on, depth write on, tri front-to-back par bucket `(mesh_id, material_id)`) → Capture conditionnelle (blit-to-buffer post-present, activée par `--smoke-test`). Pas de transparent pass.
- **Shader pipeline** dans `src/modules/render/shader_pipeline/` — compilation offline GLSL → SPIR-V via spawn `glslc` CLI, cache disque hashé sur `(source + defines + glslc_version)`, hot-reload runtime via filewatch + re-spawn `glslc` dans un thread dédié. Latence hot-reload cible < 200 ms. Pas de binding shaderc / glslang. SPIR-V commité dans `assets/shaders/`, régénération via `zig build shaders` opt-in.
- **Instancing + batching ECS CPU-side** dans `src/modules/render/instancing/` — bucketing par `(mesh_id, material_id)` via `std.HashMap`, upload Transform en instance buffer par bucket, un drawcall instancié par bucket. Tri front-to-back par profondeur du centroïde de bucket.
- **Suppression `src/spike/ppm.zig`** (dette D-S2-ppm). Capture frame route via offscreen render target R8G8B8A8_UNORM dans la GAL, readback CPU + conversion → PPM RGB en mode `--smoke-test`. Lifecycle : créé en mode capture, libéré au teardown.
- **Extension `tools/vk_gen/` — émetteur `*Raw` variants** (dette D-S2-dispatch-bypass). Pour chaque fonction Vulkan dont au moins un paramètre n'est pas exposé proprement par le wrapper idiomatique (pointer sentinel optionnel, pNext chain), émettre deux variants : le wrapper idiomatique + un `*Raw` qui expose tous les paramètres bruts. Cible explicite : `vkAcquireNextImageKHR`, `vkQueuePresentKHR`, `vkAcquireNextImage2KHR`. Migration du code render vers les wrappers idiomatiques uniquement.
- **Extension `tools/vk_gen/` — whitelist closure transitive** (dette D-S2-vk-whitelist). Algorithme reachability fixed-point depuis l'ensemble des fonctions/extensions whitelistées. Filtrage à l'émission des types et variants d'enum non atteignables. Cible : lignes `src/core/platform/vk.zig` post-closure **≤ 50 % du baseline pré-closure** (baseline mesuré en début de milestone). Clause d'ajustement : si la mesure post-implémentation révèle un plancher technique (impossible de descendre sous le seuil sans casser une fonctionnalité whitelistée), documenter la mesure et le pourquoi du plancher dans `Notable items for review` du squash commit, ajuster le seuil via déviation actée dans la SECTION VIVANTE (pas de re-spec mid-milestone).
- **VkResult aliases déplacés dans enum** (dette D-S2-vkresult-aliases). Retrait complet des `pub const VK_*: Result = .xxx` au scope module. Migration mécanique des call sites vers `vk.Result.success`, `vk.Result.error_out_of_host_memory`, etc.
- **Suppression `src/spike/vk_frame.zig`** absorbé par `gal/vulkan/swapchain.zig` + `gal/vulkan/frame.zig`. **Suppression `src/main.zig`** (le moteur Weld est consommé comme lib + outils, pas comme binaire racine). La démonstration publique de la GAL vit dans `examples/triangle/` (sous-projet standalone avec son propre `build.zig` qui consomme Weld via `b.dependency("weld", ...)` — test architectural vivant de l'API publique du point de vue d'un consommateur externe). Si M0.8 (vertical slice) a besoin d'un binaire, il vit dans `examples/vertical_slice/` (cohérent avec `engine-phase-0-criteria.md §C0.8`).

## Out-of-scope

- **V-Buffer (Visibility Buffer)** — Phase 1. La GAL doit l'accommoder sans refactor, mais l'implémentation reste forward classique en M0.4.
- **Facet (virtual geometry, Nanite-like)** — Phase 3+.
- **Radiance (GI)** — Phase 1+ (BakedLightmaps), 2+ (RadianceCascades, SurfelGI), 3+ (PathTracer).
- **Stochastic visibility / shadows** — Phase 1+. Pas de shadow map Phase 0 (la scène M0.4 n'a pas d'ombres).
- **Post-process pass** — Phase 2+. Pas de bloom, tone mapping, motion blur, etc.
- **Transparent pass** — Phase 1+. La scène M0.4 est 100 % opaque.
- **MSAA** — Phase 1+ en mode Forward+. Sample count fixé à 1× en M0.4 (le champ `sample_count` est présent dans `TextureDescriptor` / `RenderPipelineDescriptor` côté API publique mais toute valeur > 1 retourne `error.Unsupported` Phase 0).
- **Bindless descriptors / descriptor indexing utilisé** — escape hatch déclaré jour 1 dans la surface GAL, **non exploité** Phase 0 (bind groups fixes uniquement).
- **Indirect draw / GPU-driven culling** — Phase 1+.
- **Mesh shaders, task shaders** — Phase 3+ (Facet).
- **Ray tracing** — Phase 2+ (GI optionnelle).
- **Compute shaders exécutés** — la GAL expose `ComputePipeline` et `ComputePassEncoder` jour 1, mais aucun usage compute n'est livré en M0.4 (premier usage Phase 1 culling/GI).
- **Backends Metal, D3D12, WebGPU** — types et interfaces déclarés jour 1 (escape hatches respectifs sur le contrat de chaque backend), implémentation Phase 2-3.
- **Compilateur Etch Shader** — Phase 1+. Les shaders M0.4 sont écrits en GLSL et compilés via `glslc` CLI. Le pipeline canonique Etch Shader → SPIR-V ne s'active qu'en Phase 1+, à ce moment-là il alimente la GAL avec du SPIR-V — l'API GAL côté input shader ne change pas.
- **Binding C `shaderc` ou `glslang`** — refusé. La liste des 7 keepers C reste inchangée (cf. `engine-c-bindings.md §6.4` + analyse §Notes).
- **Reflection runtime du SPIR-V** — pas de SPIRV-Cross runtime. Les layouts UBO/SSBO/textures sont déclarés explicitement dans `PipelineDescriptor` (pattern WebGPU).
- **SPIRV-Cross / DXC invocation pour MSL/DXIL/WGSL** — Phase 2+ (cooking offline lors de l'introduction des backends correspondants).
- **macOS / iOS / Android / Web** — Phase 2+. `src/core/platform/window/stub.zig` continue à retourner `error.UnsupportedPlatform`.
- **Refactor de l'asset pipeline** — M0.5. La compilation GLSL→SPIR-V en M0.4 est un standalone `tools/shader_compiler/` invoqué par `build.zig`, pas une intégration dans l'asset pipeline canonique.
- **Material Instances, MaterialGraph, shading models multiples** — Phase 1+. Phase 0 : un seul shader trivial (vertex + fragment standard) pour le triangle/cube de démo et le benchmark instancing.
- **Modification de l'interface `Window` Tier 0** — livrée en M0.3, non touchée en M0.4.

- `zig build run-example-triangle` (sans flags) — ouvre une window, affiche un triangle (ou cube simple) animé via la GAL Vulkan, tourne à 60+ FPS sur Fedora 44 + GTX 1660 Ti, sortie propre sur close/Ctrl+C

## Notes

**Décisions architecturales actées (résumé des 10 axes traités en conversation Claude.ai du 2026-05-26)** :

1. **GAL WebGPU-like + escape hatches pré-câblés jour 1** : la surface publique accommode `TimelineSemaphore`, `BarrierExplicit`, `DescriptorIndexing` dès M0.4 (types présents, fonctionnels minimaux Vulkan, no-op Null). Sans ce pré-câblage Phase 0, l'ajout Phase 1+ forcerait un refactor de toute la surface — viole le principe directeur "concevoir au jour 1".
2. **Auto-tracking des barriers par défaut, `BarrierExplicit` opt-in** : Phase 0 a 2 passes + 1 blit conditionnel, auto-tracking suffit largement. Phase 1+ le render graph DAG aura besoin du mode explicit pour pass merging et resource aliasing.
3. **SPIR-V uniquement en input GAL** : pas de HLSL/WGSL source, pas de reflection runtime SPIR-V (layouts déclarés explicitement, pattern WebGPU). Source HLSL/WGSL reportée Phase 2+ et seulement si demande externe documentée.
4. **Backends M0.4 : Vulkan + Null. Metal/D3D12/WebGPU = jour 1 dans le design (types + interfaces), pas dans l'implémentation.**
5. **Render graph 3 passes Phase 0** : Depth prepass (D32_SFLOAT, pas de stencil) → Forward opaque (tri front-to-back par bucket) → Capture conditionnelle (post-present). Pas de MSAA. Pas de transparent.
6. **Capture frame format R8G8B8A8_UNORM** (pas BGRA) — conversion CPU vers PPM RGB triviale (drop alpha, écrire RGB octet par octet).
7. **Shader compilation : GLSL → `glslc` CLI spawn + cache disque hashé + filewatch + re-spawn pour hot-reload. Pas de binding shaderc / glslang.** La règle "7 keepers C cible finale" reste inchangée. Critère §6.4 #3 (consumed by runtime jeu shipping) échoue pour shaderc qui serait dev-only conditionnel. Latence hot-reload `glslc` spawn ~100 ms par shader, sous le seuil de friction humaine 200 ms.
8. **Pipeline canonique cible long-terme : Etch Shader → SPIR-V (Phase 1+ via compilo Etch)**. M0.4 utilise GLSL parce que le compilo Etch n'existe pas encore. L'API GAL côté input shader est `createShaderModule(spirv_bytes: []const u8)` — elle ne change pas quand le compilo Etch arrivera Phase 1+, seul le producteur de SPIR-V change.
9. **Batching ECS CPU-side obligatoire Phase 0** : sans batching, 100 k entités à 60 FPS est exclu (overhead CPU/driver par drawcall ~3-10 µs plafonne à ~5-15 k drawcalls/frame). Algorithme Phase 0 : bucketing par `(mesh_id, material_id)` via HashMap, un drawcall instancié par bucket. Pas de GPU-driven (Phase 1+).
10. **Pas de trigger split réactif** (règle non-négociable cf. userMemories). Si dépassement contexte/scope observé par Claude Code en cours de session, position défaut = continuer dans la même session. Hotfix M0.4.X.1 possible **après merge** si régression urgente, pas pendant.
11. **Deux flags de sélection Vulkan distincts** (décision post-Axes, 2026-05-26) : `--gpu-prefer=<discrete|integrated|index:N>` inchangé vs S2 (sélecteur hardware), `--vulkan-driver=<auto|hardware|software>` nouveau (sélecteur d'implémentation). Composabilité : `--vulkan-driver=hardware --gpu-prefer=integrated` est un cas d'usage valide ("force iGPU, jamais lavapipe fallback"). Fusion en un seul flag élargi rejetée parce qu'incapable d'exprimer ce conflit proprement. Conflits explicites loggés en warn, pas en erreur.
12. **Suppression `src/main.zig`, structure `examples/triangle/` standalone** (décision post-Axes, 2026-05-26) : le moteur Weld est consommé comme lib + outils, pas comme binaire racine. La démonstration GAL vit dans un sous-projet `examples/triangle/` avec son propre `build.zig` qui consomme Weld via `b.dependency("weld", ...)`. Triple bénéfice : (a) test architectural vivant de la consommabilité externe de l'API GAL dès jour 1, (b) référence d'usage public pour les futurs consommateurs, (c) clôture de la dette "src/main.zig spike S2" sans la conserver indéfiniment. Pattern à généraliser pour M0.8 `examples/vertical_slice/`.
13. **Seuil whitelist closure ≤ 50 %** (décision post-Axes, 2026-05-26) : seuil 60 % rejeté comme trop laxiste (1 % de marge sur la cible notable item M0.3 de ~3500 lignes économisées). 50 % force un algorithme rigoureux de propagation transitive. Clause d'ajustement par déviation tracée dans la SECTION VIVANTE si plancher technique documenté.

**Estimation volume** (indicative, à raffiner) : 8 100 - 12 100 lignes ajoutées (~2-3× M0.3). Sous-livrables : GAL interface + types ~1500-2000, backend Vulkan ~2500-3500, backend Null ~300-500, render graph ~800-1200, shader pipeline ~400-600, instancing ~500-800, 6 dettes bindgen ~600-1000, tests + benchmarks ~1500-2500, `examples/triangle/` (build + main + manifest) ~250-350.

**Pattern artefacts générés commités** (cohérent avec bindings Vulkan/Wayland) :
- SPIR-V des shaders moteur commités dans `assets/shaders/*.spv`
- Régénération opt-in via `zig build shaders`
- `glslc` est une peer dependency **uniquement** pour `zig build shaders` (régénération) ou pour le hot-reload runtime dev. Le build standard `zig build` ne dépend pas de `glslc`.
- CI step `shaders-check` garantit l'absence de drift entre `.glsl` et `.spv` commités.
- Si `glslc` absent et hot-reload tenté → log `warn: glslc not found, hot-reload disabled, runtime continues with cached .spv`. Pas de crash.

**Premier milestone d'application de la règle §4.5.1** : ce milestone exerce pour la première fois le pattern CI runtime sémantique (weston headless + lavapipe) + gate manuelle GPU obligatoire sur les 3 configs. Risque structurel à surveiller : si la CI runtime sémantique se révèle fragile (compositor headless flaky, lavapipe rendu non-déterministe), patcher §4.5.1 en conséquence avant de propager la règle aux milestones suivants.

**Risque architectural** : la GAL est un point de bifurcation. Si la surface publique se révèle mal pensée pour Metal/D3D12 Phase 2, le refactor coûte 5-10× le coût initial. La discipline du brief : **figer la surface publique par contrat écrit** dans M0.4. L'implémentation derrière peut bouger Phase 1+ sans que les call sites des modules consommateurs cassent. Si en cours de M0.4 Claude Code identifie une faiblesse structurelle de la surface, **stop + retour Claude.ai** plutôt que patch in-place. Le sous-projet `examples/triangle/` sert de canari : si y faire tourner un triangle réclame plus de 200 lignes côté caller, c'est un signal de faiblesse de la surface publique.

**Pièges connus à éviter** :
- Ne pas implémenter un seul backend (Vulkan) en croyant "abstraire plus tard" — anti-pattern explicite, le Null backend force le décollage de l'interface dès jour 1.
- Ne pas exposer de types Vulkan natifs (`vk.VkBuffer`, `vk.VkDevice`) dans l'API publique GAL — ils doivent rester strictement encapsulés dans `gal/vulkan/`. Le linter doit y veiller.
- Ne pas oublier la fence/semaphore négociation côté swapchain (binary semaphore pour `vkAcquireNextImageKHR` / `vkQueueSubmit` / `vkQueuePresentKHR` — `TimelineSemaphore` est l'escape hatch Phase 1+).
- Le pipeline cache disque Vulkan (`VkPipelineCache`) doit être chargé/sauvegardé entre runs sinon les recompilations de pipeline cassent les FPS au démarrage.
- Le hot-reload doit recréer le pipeline complet (pas juste le shader module) — sinon Vulkan validation layers râlent à raison.
- `examples/triangle/` ne doit jamais importer un module Weld interne (`@import("../../src/modules/render/gal/vulkan/device.zig")` etc.). Seule la surface publique exposée via `b.dependency("weld", ...)` est autorisée. Linter ou structure de build doit garantir cette isolation.

**Hors-scope explicite à ne pas étendre** : si en cours de session Claude Code ressent le besoin d'ajouter un système complet (post-process pass, transparent pass, V-Buffer naïf, GPU culling) "tant qu'on y est", refuser et tracer la dette pour Phase 1+. Le scope figé est strictement ce qui est listé dans §Scope.

- **Découpage en 11 sous-livrables structurels** chacun commitable, testable, lintable indépendamment. Chaque commit produit un état vert end-to-end (build + test + fmt + lint), permettant un workflow incrémental sans état intermédiaire cassé.
- **Examples/triangle/ comme test architectural vivant** (brief §Notes décision 12). Le sous-projet standalone (≤ 200 lignes côté caller, vérifié 157) consomme la surface publique GAL via `b.dependency("weld", ...).module("weld_render")` et tourne via `zig build run-example-triangle -- --smoke-test`. La consommabilité externe de l'API est validée comme contrat exécutable.
- **Découverte critique tracée** : bugs Zig 0.16 API (`std.process.Child.init`, `std.fs.cwd`, `std.fmt.fmtSliceHexLower`, `std.time.nanoTimestamp`) masqués par la lazy analysis Zig 0.16 — révélés par le tool standalone shader_compiler qui force l'analyse des fns pub. À traiter en discipline d'enforcement (cf. conventions §13 lazy analysis guard).

### Ce qui a dévié de la spec d'origine

- **Seuil whitelist closure ajusté de ≤ 50 % à -17 %** (déviation actée dans la SECTION VIVANTE, commit `1aa181c`). Plancher technique documenté : ~3 400 lignes proviennent des packed structs de bitmasks Vulkan qui doivent maintenir leur largeur ABI 32/64 bits avec champs `_reserved_N`. Réduction supplémentaire demanderait un refactor représentation bitmask (raw u32 + constantes) cassant l'API publique `vk.SomeFlags.empty`/`.flag_name` consommée par 200+ call sites — trade-off rejeté Phase 0. Re-évaluation Phase 1+.
- **Backend Vulkan opérationnel jusqu'au point de présentation, pas au-delà**. La création + teardown du Device fonctionne (offline test vert sur lavapipe). L'intégration window↔surface (conversion `*platform.window.Window` → `gal.types.SurfaceHandle`) reste à câbler pour que `examples/triangle/` rende un vrai triangle via Vulkan plutôt que le Null backend. **Marqué dette résiduelle ci-dessous**.
- **Le scoring multi-GPU + sélection `--vulkan-driver=<auto|hardware|software>`** est implémenté dans `gal/vulkan/device.zig` mais pas testé sur les 3 GPU configs Fedora — la validation manuelle §4.5.1 est non-bloquante pour le merge selon brief (couverte par les configs Fedora ; Win11 unavailable).

### Ce qui est à signaler explicitement en review

1. **Wiring window→surface Vulkan manquant** : `examples/triangle/` utilise actuellement le backend Null comme défaut. La conversion d'un `*platform.window.Window` Tier 0 vers une `gal.types.SurfaceHandle` n'a pas été câblée — c'est la pièce structurelle restante pour que le triangle Phase 0 soit rendu via Vulkan dans `examples/triangle/`. Estimation 100-200 lignes (un helper côté `gal/vulkan/surface.zig` qui appelle `vkCreateWin32SurfaceKHR` ou `vkCreateWaylandSurfaceKHR` selon la plateforme, exposé via la surface publique GAL).
2. **Déviation seuil whitelist closure** (cf. ci-dessus + commit `1aa181c`). À tracer dans le Notable items for review du squash commit.
3. **Bench `bench/render_instancing.zig` + golden PPM différés** — exigent un Vulkan opérationnel sur Linux + lavapipe, donc bloqués sur l'item (1). Tracés comme dette M0.4.X.1 ou M0.5 selon urgence Phase 0.
4. **Validation manuelle GPU §4.5.1 sur 3 configs** : 2 configs Fedora + Win11 unavailable (machine down). Comme M0.4 est le **premier milestone d'application** de §4.5.1, le verdict GO/NO-GO consigné dans la PR doit explicitement attribuer chaque config (cf. brief §CI + §4.5.1 indisponibilité hardware).
5. **CI runtime-smoke-test step non câblé** dans `.github/workflows/` — l'infra weston headless + lavapipe + diff PPM bit-à-bit reste à scripter. Brief §CI catégorise ce step comme **bloquant** pour les milestones renderer/GPU futurs — à finir avant le tag final M0.4 ou tracer comme dette M0.4.X.1.
6. **Lazy analysis guard découvert avec retard** : compiler.zig/cache.zig/hot_reload.zig étaient broken silencieusement parce que les fn pubs n'étaient jamais exercées depuis le test root. Le tool standalone shader_compiler a forcé la détection. Discipline d'enforcement : tout module qui ajoute des `pub fn` doit avoir au moins un test inline qui les appelle (le comptime pin via `_ = mod.foo;` ne suffit pas — il faut un appel runtime ou comptime explicite).
