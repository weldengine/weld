## Context

Closes the EBNF v0.6 execution gap for collection-typed `resource` fields (C1.6). `etch-reference-part1.md` §5.5 already sanctions `resource GameSettings { recent_servers: string[] }`, but the type-checker rejects every collection field type on components *and* resources (the E1 POD-strict ruling in `src/etch/types.zig`), and the tree-walker has no persistent collection representation — collections live only in the rule arena and are reset at the body boundary. This milestone delivers declare → load → read → mutate → persist → drop for `T[]`, `[K: V]` and `Set<T>` as resource fields, on the persistent heap with a `type_id`→drop and a refcount shared with the resource (`etch-memory-model.md` §1.2 / §4.3 / §5.4 / §6.7). The "long-life closures" half of the plan row is refused — no executable escape surface exists in the Phase-1 tree-walker (see Notes).

## Notes

- **Closures half refused — no gap.** Ground-truth at `v0.10.16-resolver-completion`: the tree-walker has exactly two `Value.closure` consumers, both synchronous same-body invocations (`callZeroArgClosure` for the `tick_until` predicate; the `.fn_call` E1 path). No EBNF v0.6 executable surface stores a closure beyond its rule body — `fn(...)` field types are rejected at type-check (a non-`.named` field type node), widgets are not executed by the interpreter, and escaping is a Phase-2 HIR/bytecode lowering (`etch-memory-model.md` §5.6). The timer/task snapshot path (`cloneLocalsInto`) is a shallow copy sharing the rule-arena referent — the generic POD-across-suspend caveat, identical for arrays and structs, not a closure-specific gap. Per the plan's own guard and the M1.0.16 no-dead-code doctrine, this half collapses.
- **Persistent representation (decision A).** Distinct persistent Value tags mirror the proven `.string_run` (rule-arena) vs `.string_persistent` (persistent) split: the zone is known at the tag, there is no runtime discriminant, and the drop is dispatched by `type_id`. A "persistent bit on the existing handle" was rejected — it puts a runtime discriminant into a heterogeneous store and breaks `etch-memory-model.md` §1.2 ("the value's zone is part of its internal type").
- **Tier-0 drop registry (decision a).** `persistent.zig` stays decoupled from Etch: it exposes `DropFn` + `registerDrop`, and the interpreter registers the collection drops at init. `runDrop` cannot reinterpret a block payload as an Etch `ArrayListUnmanaged(Value)` — that would couple Tier 0 to Etch. This corrects the stale `runDrop` comment (which pointed at the right place but would have broken Tier-0 purity). The registry realizes the "open TypeId set" the module already advertises.
- **Persistent container = the block payload.** A collection block's payload is the owned container (`ArrayListUnmanaged(Value)` for array / set, `ArrayListUnmanaged(MapPair)` for map); its internal buffer is a `gpa` allocation the container owns. The `CollectionSlot { ptr: u64 }` in the resource field holds the block pointer — stable across `append` / realloc (the buffer moves inside the block; the block pointer does not). A read returns a borrowed `*_persistent = ptr` without incref — safe for the rule body because the resource, hence the block, outlives it (the `.string_persistent` read precedent in `value.zig`). The registered drop decrefs string elements / keys / values, `deinit`s the container, then the block is freed by `persistent`.
- **Promotion is load-bearing.** Any string entering a persistent collection (push / insert / reassignment) is deep-copied into a fresh persistent string, following `promoteResourceString`'s order: read old → alloc + copy new → write slot → decref old. A `.string_run` (rule-arena) or `.string_persistent` element that escaped its body without this copy is the M1.0.14 / M1.0.15 use-after-free class — gate escapes with `stringNeedsOwning`. POD elements (`int` / `float` / `bool` / enum) are stored inline.
- **Element bound.** Resource collection element ∈ {POD scalar, `string`, enum} — the exact resource scalar-field surface (M1.0.3). Nested collections are rejected (`E0222`).
- **Acceptance anchored on proven code (M1.0.16 lesson).** The whole persistent-field path is modeled on the M1.0.3 `string`-field precedent, which is tested and green (`resource string field is mutable and the previous value is released`): read/write via `readResourceField` / `writeResourceField`, persistent promotion via `promoteResourceString`, `StringSlot` teardown at `deinit`. Collections extend that path; they do not invent one.
