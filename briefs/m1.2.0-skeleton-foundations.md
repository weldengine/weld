## Context

Kinesis does not exist. Measured at `2006ed0`: no `src/modules/kinesis/`, no `src/interfaces/AnimationModule.zig`, and every occurrence of `skeleton` under `src/` means "code skeleton". Of the eleven frame-pipeline stages of `engine-animation-kinesis.md` §4, zero are implemented. This milestone opens the module and delivers the bottom of the dependency chain: a skeleton asset, its hierarchy, its bind pose, forward kinematics, and the one addressing type through which every later bone reference must pass.

It also settles a decision that becomes expensive seven sub-milestones from now. `PoseBuffer` crosses `sampleClip`, `blendPoses` and `additivePose`, so it freezes with `AnimationModule` at M1.2.7, and it is snapshotted by rollback. Its memory layout — AoS or SoA — was asserted in three documents and measured in none. **This milestone decides it by benchmark, at the first gate, before any consumer exists.** Changing it later is a re-opened frozen interface plus a save-format migration.

## Scope

- `Mat4` descends into `src/foundation/math/mat4.zig` and `src/core/rtti/type_info.zig` imports it. The type already exists in `rtti` with a frozen layout — `extern struct { m: [16]f32 }`, column-major, 64 bytes pinned by test — and a twin in the plugin C surface (`WeldMat4`, `src/core/plugin_loader/desc.zig`). **The layout and the twin are preserved byte for byte; only the declaring file moves.** No second `Mat4` is created: `core` imports `foundation` and never the reverse, so a mathematical type declared in the reflection module is at the wrong tier, beside `Mat3` which is already at the right one.
- `Mat4` operations, generic over the scalar on the `Mat3(T)` pattern: multiply, TRS composition, affine inverse, transpose, and conversion from a `(translation, rotation, scale)` triple. Column-major storage, matching `Mat3` and the existing `Mat4`.
- A micro-benchmark deciding the `PoseBuffer` layout: N-bone pose blend, AoS against SoA, on `src/foundation/simd/`. **The measured number decides, and it is published in the gate and written into `engine-animation-kinesis.md` §2 by a Claude.ai round-trip.** Both variants are implemented for the measurement; only the winner survives the gate.
- The Kinesis Tier 1 module: `src/modules/kinesis/`, `init` / `deinit` taking `*core.ModuleContext`, component and resource registration through `world` and nothing else, system registration through `ctx.system_scheduler`.
- `src/interfaces/AnimationModule.zig` in partial form, **explicitly not frozen**: the entries this milestone implements are asserted, the rest are typed stubs returning `error.NotImplemented`. The freeze is M1.2.7 (`engine-phase-1-criteria.md` C1.0); this file carries a marker saying so, so that no reader mistakes an existing file for a frozen signature.
- The skeleton asset format: header, bone count, parent index array, bind pose, inverse bind pose, optional `SkeletonProfile` block. Loading **rejects** a malformed hierarchy rather than repairing it: out-of-range parent index, cycle, a parent appearing after its child, more than one root.
- The topological order is an **asset invariant checked at load**, not a runtime tolerance: parents precede children, which is what makes forward kinematics a single linear pass with no sort and no recursion.
- Forward kinematics: local poses → world poses, composing `Transform` through the parent chain, non-uniform scale included. Inverse bind pose stored and exposed; it is the input `getSkinMatrices` will need at M1.2.3.
- `BoneRef`, `BoneRole` and `resolveBone` (`ARCH-033`). A `BoneRef.role` whose role is unmapped resolves to **absence**, never to an arbitrary bone. A skeleton with no `SkeletonProfile` stays fully usable through `BoneRef.name`.
- Counter-proofs shipped by the gate that introduces each guarantee, each paired with a positive witness in the same run. For `resolveBone`, the attack is written **before** the counter-proof (`D37`).

## Notes

**The gate order, and why it is this one.**

- **G1 — `Mat4` descends, and the pose layout is decided.** The benchmark needs `Vec`, `Quat` and `Mat4` and nothing else: not the module, not the asset, not FK. Placing the most structuring decision at the cheapest gate is deliberate — every later gate consumes its result, and taking it after the FK is written means writing the FK twice. The gate publishes both layouts' numbers on blend AND on FK, then states the ruling and its margin. **If the two measurements disagree** — blend favouring SoA and FK favouring AoS by comparable margins, which is the expected shape — the gate reports and stops: arbitrating a split verdict is a design call weighted by how often each runs in the frame, and that belongs to Claude.ai.
- **G2 — the module and its interface file.** Registration through `ModuleContext` and its four fields; no second route to component registration, no `registrar`, no `event_bus`. The interface file exists but carries a not-frozen marker.
- **G3 — the asset format and its rejections.** Before any runtime hierarchy, because the rejections define what the runtime is allowed to assume. A loader that repairs a malformed hierarchy makes every downstream invariant untestable.
- **G4 — hierarchy, bind pose, inverse bind, forward kinematics.** On the layout G1 decided. Non-uniform scale is exercised in the FK test and not deferred: it is the case that separates a correct composition from one that happens to work on unit scale.
- **G5 — `BoneRef`, `BoneRole`, `SkeletonProfile`, `resolveBone`.** The attack before the counter-proof, stated as an order and not as a preference.

**Three spaces, named, because confusing them is the classic bug of this module.**

Local (a bone's transform relative to its parent), skeleton-relative (relative to the skeleton root, what FK produces), and world (skeleton-relative composed with the entity's `Transform`). `Skeleton.current_pose` holds the first, `Skeleton.world_pose` the second. The entity transform enters at the consumer — `getSkinMatrices` at M1.2.3, `getSocketTransform` at M1.2.6 — and **not** inside FK. Writing FK so that it bakes the entity transform in makes both later entries wrong in a way that looks right on an entity at the origin.

**Pose lifetime.**

A `PoseBuffer` is variable-length; a component is a POD `extern struct` (`engine-zig-conventions.md` §16). The buffer therefore lives outside the ECS, in module-owned storage allocated from `ctx.persistent_allocator`, and the `Skeleton` component carries a handle. The precedent is `PhysicsWorldRef` in `src/modules/forge/sync.zig`: the world lives outside, a resource carries the pointer, the ECS knows nothing of it. **Do not reach for a Tier 0 ECS change to store poses.**

**Traps recorded.**

`Mat4` exists already. The first recon of this milestone claimed it existed nowhere, having grepped `src/foundation/` and `src/modules/render/` while asserting something about the whole tree — `D36`, the selector wider than its subject, found by external review. It is in `src/core/rtti/type_info.zig:175`, it is column-major, it is 64 bytes pinned by a test at line 208, it is mirrored by `WeldMat4` in `src/core/plugin_loader/desc.zig:84`, and `src/core/rtti/comptime_builder.zig:134` maps it to `.mat4`. **Moving it must change no byte of its layout and no behaviour of the reflection path.**

The type of a pose has borne three names across three documents — `PoseBuffer`, `BonePose`, `SoaTransform` — and two contradictory layouts. The corpus was unified on `PoseBuffer` on 2026-09-13. If any spec read at step 2 still says otherwise, the corpus copy is stale: stop and report rather than implementing what it says.

`ARCH-033` names one exception: the `on_bones` production of the `anim_graph` construct takes literal strings, ratified in M0.8 and carried by `src/etch/ast.zig` (`AnimLayerProp`). It is not a violation to fix, and this milestone does not touch it.

A counter-proof suite is green when nothing compiles at all. Every non-compilation case is paired, in the same execution, with a case that must compile and whose success is asserted.

## Execution log

### G1 — `Mat4` descends, and the pose layout is decided — CLOSED 2026-09-13

**`Mat4` moved, and it moved as an ALIAS rather than a re-declaration.** `src/foundation/math/mat4.zig`
declares `Mat4(T)` and `Mat4f`; `src/core/rtti/type_info.zig` now reads `pub const Mat4 = math.Mat4f;`.
The alias is load-bearing and not cosmetic: `comptime_builder.classifyField` matches on type
IDENTITY (`T == Mat4`) before its structural switch, so a second declaration of the same shape would
have reclassified every reflected `Mat4` field as `.nested_struct` in silence. Measured on the
tree: two declarations of that shape exist (`rtti.Mat4`, `desc.WeldMat4`), plus two aliases
(`rtti/root.zig:69`, `comptime_builder.zig:45`); `Mat4f` existed nowhere.

**Storage diverges from `Mat3(T)` deliberately.** `Mat3(T)` is `cols: [3]Vec(3, T)`, `@Vector`-backed
and therefore without a language-defined byte layout. `Mat4f` cannot afford that — it is the
reflected `.mat4` kind AND it mirrors `WeldMat4` on the plugin C surface — so it is
`extern struct { m: [16]T }`, flat and column-major, byte-identical to what `type_info.zig` carried.
The reason is written at the file head so nobody harmonises the two shapes by symmetry.

**The C twin had NO assertion tying it to `Mat4`, and now it has one.** Measured: `WeldMat4` has zero
use sites and was related to `rtti.Mat4` by a doc comment only, so no compilation anywhere would have
noticed the two diverging. `tests/foundation/math/mat4_test.zig` compares them field by field — names,
types, offsets, size, alignment — with `WeldMat3` as the witness that the comparison can return false.
The pre-existing guard was `@sizeOf == 64` and nothing else, which a reshuffle inside 64 bytes passes.

**One defect found by the tests, and a diagonal fixture would have missed it.** `affineInverse` dotted
the COLUMN of the inverse block with the translation where the formula wants the ROW. The two coincide
for every diagonal block, so a fixture with identity rotation and axis-aligned scale passes either way;
the round-trip test carries a rotation AND a non-uniform scale, and it failed. Fixed, and the reason is
written at the site.

#### The layout ruling — **SoA-3**, three arrays one per component

`zig build pose-layout-bench`, ReleaseFast, 9 interleaved rounds × 20 000 iterations, median per round.
Ratios are `layout / AoS`; below 1 means faster than AoS.

| | 32 bones | 64 bones | 128 bones |
|---|---|---|---|
| **Blend** — SoA-3 | 0.955× | 0.936× | 0.961× |
| **Blend** — SoA-channel | 1.747× | 1.756× | 1.777× |
| **FK** — SoA-3 | 0.930× | 0.932× | 0.944× |
| **FK** — SoA-channel | 1.069× | 1.088× | 1.089× |

**THE TWO MEASUREMENTS DO NOT DISAGREE, so the gate's stop condition does not fire.** SoA-3 wins both
operations at all three bone counts. Sign checked over three full runs, eighteen measurements: every
SoA-3 ratio is ≤ 1.006 and seventeen of eighteen are strictly below 1. Margin 4–9 %.

**An instrument defect was found and fixed BEFORE the ruling was read.** The first version looped over
`[3]f32` elements on the AoS side while the SoA side used `Vec3.add`/`scale` — one body written scalar
against one written vector, which credits the layout with a difference the code made. Equalised so the
only difference is where the bytes live. It mattered: the 32-bone blend ratio moved from 0.936× to
1.006×, and the anti-DCE checksums were IDENTICAL across the rewrite (blend 1476.306864,
fk 282.303567), which is what proves the change touched the code shape and no answer.

**And the corpus's own argument for SoA is REFUTED by the measurement.** The stated reason to prefer SoA
is vectorisation, and the only form that vectorises — ten scalar channels — is the one that loses, by
75 % on the very operation the argument was about. What SoA-3 actually buys is three contiguous streams;
it is the same 48 bytes per bone as AoS, so the win is locality, not footprint and not width.

**A third layout was measured where the frozen Scope names two.** Reported rather than folded in: had
only the corpus's SoA-3 been measured against AoS, the ruling would have rested on a comparison that
never gave the vectorisation argument its own form. The third row is what lets the refutation above be
stated instead of assumed.

**Closing measurements.** Test floor 2290 → **2300** (2298 on `windows-2025`), re-derived FROM THE SUITE:
`zig build test --summary all` reports `2281/2300 tests passed (19 skipped)` on macOS and the dead-test
closure arrives at 2300 independently — the guard refused the old number and the two computations were
reconciled on the suite, never on each other. Four corners green (Debug/ReleaseSafe × f32/f64),
`zig build lint` green, `zig fmt --check` green, `zig build` clean with zero warnings.

#### The ruling CORRECTED — **interleaved, with `@Vector`-backed elements**

**The SoA-3 verdict one section above is WRONG, and a fourth layout is what showed it.** The three
layouts compared so far differed in TWO things at once: memory order (interleaved against split) AND
element representation. The AoS row stores `Transform`, whose members are `[3]f32` / `[4]f32` because
it is an `extern struct` POD; the SoA rows store `Vec3` and `Quat`, which are `@Vector`-backed. So the
gap could belong to either, and the argument that the AoS candidate is forced to `Transform` — which is
true — does not settle which of the two the gap came from. `AoS-vec` is the control: the same
interleaving, the same 48 bytes, the same 16-byte alignment, `@Vector`-backed members, no conversion.

| | 32 bones | 64 bones | 128 bones |
|---|---|---|---|
| **Blend** — AoS-vec | 0.911× | 0.903× | 0.895× |
| **Blend** — SoA-3 | 0.954× | 0.936× | 0.937× |
| **Blend** — SoA-channel | 1.798× | 1.758× | 1.786× |
| **FK** — AoS-vec | 0.942× | 0.943× | 0.931× |
| **FK** — SoA-3 | 0.947× | 0.940× | 0.934× |
| **FK** — SoA-channel | 1.092× | 1.094× | 1.091× |

**`AoS-vec` beats `SoA-3` on blend 12 times out of 12** across four full runs, by 3 to 5 %. On forward
kinematics the two are within 0.7 % and the sign FLIPS between runs, so no verdict is registered there —
a quantity whose sign is not stable is not a result.

**The ruling therefore has two halves, and only the first was ever the question.**

1. **Interleaved, not split.** `AoS-vec` wins blend and ties FK, so it dominates `SoA-3`. The
   corpus's argument for SoA was vectorisation; the only form that vectorises loses the blend by 79 %.
2. **The element is `@Vector`-backed, not `[3]f32`** — and this is where the difference actually lived.
   The corpus's literal AoS, one Tier 0 `Transform` per bone, is the SLOWEST of the three viable forms
   by about 10 % on BOTH operations. Neither document considered this axis; both named only the first.

`PoseBuffer` is therefore one array of a Kinesis-owned element carrying `Vec3` / `Quat` / `Vec3`. The
element is deliberately NOT named `BonePose` or `SoaTransform`: both are retired names for the BUFFER,
and reusing either would rebuild the three-names-for-one-object confusion the corpus has just resolved.

**Tension reported rather than resolved silently.** The frozen § *Out of scope* says "Kinesis uses the
Tier 0 one, as Forge does" of `Transform`. Read as governing the pose buffer's internal element, it
costs the 10 % measured above; read as governing the ECS-facing surface — which is where Forge names it
— it does not reach this decision, and § *Scope* delegates the layout to the measurement in as many
words. The second reading is implemented, and the entity-facing surface keeps the Tier 0 `Transform`
exactly as the bullet says. **Guy arbitrates if the first reading was meant.**

**Method, because it is the transferable part.** Two instrument defects were found in this one bench,
both by auditing the wiring rather than the number, and the SECOND one reversed the verdict the FIRST
one had already corrected. A measurement is worth what the enumeration of its controlled variables is
worth, and the enumeration is what gets written down last and checked least.

**Owed to a Claude.ai round-trip:** the ruling above is written into `engine-animation-kinesis.md` §2 and
`engine-tier-interfaces.md` §4 (`PoseBuffer`'s form is currently shown AoS there, with the note that
"si la mesure retient le SoA, c'est ici que le changement a lieu, une fois").

### G3 — the asset format and its refusals — CLOSED 2026-09-13

**The topological order is an ASSET INVARIANT checked at load, and that is what makes a cycle
unrepresentable instead of merely detected.** A parent's index is strictly lower than its children's,
so forward kinematics is one ascending pass with no sort, no recursion and no visited set — and a
cycle needs some bone to point forward, which is exactly what the check refuses. Cycle and
parent-after-child are therefore ONE check and ONE code: a cycle is an instance of that fault, not a
second fault, and a caller told two codes for one fault looks for two.

**`error.NoRoot` does not exist, and removing it was a finding rather than a simplification.** The
test written for it failed — `{0, 0}` is refused as `ParentAfterChild`, not as a rootless hierarchy —
and reading why settled it: bone zero has no index below it, so its parent is either `no_parent`, and
there IS a root, or a real index, and `p >= i` at `i == 0` is true for every value. No input reaches
the branch. An error variant no caller can provoke is an assertion wearing an error's clothes, and
this repository has removed a dead public variant once before for that reason. It is now an assert
with the reachability argument written at the site.

**`validateHierarchy` is exported and judges its own degenerate input.** An empty slice is
`BadBoneCount` there and not only in `parse`: the entry exists for the importer, and an exported judge
that trusts its caller for the one input it cannot survive is not a judge.

**Shape before content, and it is asserted rather than ordered by luck.** Every byte is read and
bounded before the hierarchy is judged, so a truncated file is never diagnosed as a bad hierarchy —
which would send a reader to the wrong place. The truncation test cuts at every seventh byte past the
header rather than at one chosen offset, because a single cut can land on a boundary and pass.

**Trailing bytes are a refusal, not slack.** A file longer than its declared contents is one this
reader did not understand, and reading it anyway is how a version skew becomes a silent partial load.

**The inverse bind pose is STORED and not derived**, which is a decision against the cheaper option.
Deriving it from the bind pose would halve the format and make one source of truth — but it would also
force the bind pose and the rest pose to coincide, and they legitimately differ whenever a mesh was
bound in a pose other than the hierarchy's rest. That is why glTF ships both, and why re-deriving
would silently re-skin any such asset.

**The encoder lives beside the reader** so the format has ONE declarant: a writer in the test tree and
a reader in the source tree are two descriptions of one layout, and they drift. It validates nothing,
deliberately — an encoder that refused malformed input could not produce the fixtures the reader's
refusals are tested with.

**Every refusal is paired, in the same test, with a skeleton that must load.** Four rejection tests
against a loader that refuses everything all pass; the pairing is what makes each mean "this shape and
not that one". Counter-factual run: disabling the hierarchy judgement reddens all four plus the inline
one, and no positive.

**The profile's own refusals.** A role mapped twice has no answer and picking the first would make
resolution depend on the order the importer happened to write; a role ordinal past this build's
vocabulary — an asset written by a LATER build — is refused rather than read as whatever sits at that
ordinal. The partial-profile test asserts the mapping COUNT, without which a profile read as complete
would resolve every unmapped role to a neighbour.

**Closing measurements.** Test floor 2315 → **2329** (2327 on `windows-2025`). Four corners green,
`lint` green, `fmt` green, `zig build` clean with zero warnings.

### G4 — hierarchy, bind pose, inverse bind, forward kinematics — CLOSED 2026-09-13

**Three spaces, and the pass produces the middle one.** LOCAL is a bone relative to its parent — what
a clip samples into. MODEL is a bone relative to the skeleton root — what forward kinematics produces.
WORLD is model composed with the entity's own `Transform`, and it is produced by the CONSUMERS.
Baking the entity transform into the pass would make the skin-matrix build and the socket read both
wrong, in a way that looks right on an entity sitting at the origin. A test pins that the pass leaves
the local pose untouched: a pass writing over its own input looks correct on the first frame only.

**The rig and the instance are two stores, and that is what one rig backing many instances means.**
`RigId` names the immutable half — hierarchy, names, bind pose, inverse binds, profile — and
`SkeletonId` names one entity's poses. A hundred characters on one skeleton carry one hierarchy and a
hundred poses. The split is here rather than promised because owning a copy per entity would make the
sharing a refactor later instead of a store lookup. `createSkeletonInstance(bone_count)` from the
previous gate is REPLACED by `instantiate(rig)`: a rigless instance has no legitimate use, and keeping
both would leave an entry with no production caller.

**A fresh instance stands in its BIND pose, not at the identity.** An entity whose clip has not been
sampled yet must stand in a pose an artist authored; a skeleton at the identity is a heap of bones at
the origin and it looks exactly like a sampling bug.

**The single linear pass is asserted TWO ways, neither of them timing.** The topological invariant is
read off the loaded rig — a parent precedes its child, which the loader refuses to admit otherwise —
and the fixed point is asserted mechanically: running the pass a second time changes not one bit. If
a parent were evaluated after its child, the second pass would move something, because the child would
finally see a final parent.

**THE TRS COMPOSITION IS AN APPROXIMATION, and it is written down rather than left to be discovered.**
The exact product of two transforms carrying non-uniform scale contains shear, and shear is not
expressible as translation-rotation-scale — an exact pipeline would have to carry matrices, which a
pose cannot, because a matrix does not blend and blending is what the pose type exists for. Every
skeletal animation system makes this trade. A test pins the choice with a case where the two forms
visibly differ, so switching to matrices is a decision somebody takes rather than a diff that slips
through.

**The hand-computed oracle owes the engine nothing.** The chain's expected model pose is derived in
the comment from the fixture's own numbers: the spine's scale acts on the head's offset in the spine's
frame, so (0, 1, 0) becomes (0, 3, 0), and the quarter turn about +Z sends +Y to −X, putting the head
three metres along −X. The fixture is chosen so the approximation is EXACT there — a quarter turn
permutes the scale axes, so the composition has no shear — which is what lets a non-uniform scale be
exercised against an unambiguous expected value.

**The inverse-bind round trip bites because its two sides come from different places.** The
inverse-bind matrices are built from the HAND-COMPUTED model pose, and checked against the pass's own
output. An error in the pass cannot cancel itself.

**A COVERAGE HOLE WAS FOUND BY COUNTER-FACTUAL AND CLOSED.** Reversing the two operands of the
rotation composition — `child · parent` instead of `parent · child` — left the whole suite GREEN.
The reason is the fixture: the acceptance chain rotates about one axis and its leaf carries the
identity, and quaternion multiplication commutes for parallel axes and trivially for the identity. A
test with two non-parallel rotations closes it, with SEQUENTIAL APPLICATION as its oracle — rotating a
vector by the child then by the parent, which owes nothing to how `compose` spells the product — and a
discrimination guard asserting the two orders really differ on that fixture. The counter-factual now
reddens exactly that test. Dropping the parent's scale from the child's offset reddens four.

**The scenario runs as a program.** `zig build kinesis-skeleton-demo` loads the three-level chain and
prints both poses; it reports the head at `(-3.000, 2.000, 0.000)`, which is the hand-computed value.
It is also the one place the load-to-pose path runs outside `zig build test`.

**Closing measurements.** Test floor 2329 → **2339** (2337 on `windows-2025`). Four corners green,
`lint` green, `fmt` green, `zig build` clean with zero warnings.

- **Residual risks / tech debt left intentionally:**
  - **No `destroyRig`.** Rigs are released at `deinit` and nowhere else, because the only thing that
    would free one is unloading its asset and no asset lifetime reaches this module. Adding the entry
    later touches no call site. What would NOT be additive is handing out rig ids that can dangle,
    which is why the slot is kept rather than recycled.
  - **`loadRig` does not deduplicate.** The same bytes loaded twice make two rigs. Deduplication needs
    an asset IDENTITY, which belongs to the pipeline that will hand out the handles.
  - **The `Skeleton` component is registered and nothing reads it.** The registered pass walks the
    module's own instance store, because reaching the entities that carry a `Skeleton` needs a query
    and the declared-access view deliberately exposes none until its first consumer. Adding one is a
    Tier 0 change and belongs to whoever needs it; the pass's declaration says what it touches.
  - **`createSkeleton(AssetHandle)` refuses.** Resolving a handle to bytes is the asset pipeline's,
    through the module registry, and no such route exists.
  - **The interface is not frozen and says so mechanically.** Its comptime block covers thirteen
    entries, seven of them refusing stubs whose error channel exists only so they CAN refuse; the
    protocol version and the fallibility of each entry land together at the freeze.
  - **`bench/pose_layout_bench.zig` is 648 lines**, over the review guideline. Four layouts × two
    operations plus the harness; the alternative is fewer layouts, which is what produced the wrong
    ruling twice. Conscious overage, in the family of the two already merged next door.
  - **This milestone leaves NO `M1.D` entry of its own.** Every hole it opened, it closed in the session
    that opened it; the four items above are absences whose owners exist, not debts.
