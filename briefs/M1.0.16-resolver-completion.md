## Context

Two name-resolution gaps of the C1.6 plan, both at the resolver / type-check layer. **(1) Module-alias qualified access `m.Type`.** `bindImports` records the whole-module alias binding in `imported_aliases` (for `import a.b` and `import a.b as m`), but that binding is never consumed, AND the qualified syntax does not parse: `etch-grammar.md` has no qualified-path production (`base_type` is a single `TYPE_IDENT`), while `etch-resolver-types.md §3.1`/§2.3 assume `math.Vec3` resolves. `TypeNodeKind.path` is reserved in `ast.zig` but never produced. So volet 1 is a small type-position grammar addition + parser + resolver. **(2) `private` completion per §10.2** — today only direct visibility + `E0107 ImportPrivateItem` (at the import binding) exist; visibility inheritance and `W0902 PrivateTypeInPublicImpl` are missing.

**Parity bar (defines scope).** The milestone brings qualified `m.Type` to exact parity with the *selective* import form (`import a.b { Type }`) at the resolution layer, no more. The selective form resolves an imported item as a **type-name** through the central `namedTypeToResolved` (plus `validateTypeAliases` and `checkComponentInstance`); it is proven to resolve in the **type-alias target** position (`type HA = Health`, the M1.0.7 test). It does **not** make imported types usable in expression-position struct literals, nor does it lift the POD rule for component-as-field — those are pre-existing limitations of the whole import system, shared by the selective form, and are **not** what this milestone adds. Qualified access plugs `imported_aliases` into the same consult sites `imported_symbols` uses, inheriting exactly the selective form's reach.

**Layer bar.** This is a resolver / type-check milestone (resolution + diagnostics under `validateProject`). The interpreter is single-file (`Interpreter.compile` takes one AST); runtime cross-module execution is out of scope for both import forms.

## Scope

- **Grammar production (spec + parser), type position only.** Add `qualified_path = IDENT , "." , TYPE_IDENT` as a `base_type` alternative in the EBNF. The parser produces the reserved `.path` `TypeNode` (`{ alias: StringId, member: StringId }`, following the `NamedTypeNode` slab convention) wherever a `type` is parsed. **No** expression-position production, **no** `struct_literal` head change.
- **Volet 1 — qualified type-name resolution.** Consume `imported_aliases` at the three sites that consume `imported_symbols` today: `namedTypeToResolved` (the central type resolver), `validateTypeAliases`, and `checkComponentInstance`. A `.path` TypeNode `m.Type` resolves `m` against `imported_aliases` (whole-module alias → target file index), then looks `Type` up in that file's `project.exports`, returning the resolved kind. Because `namedTypeToResolved` is the central resolver, qualified types then resolve in exactly the positions selective types do — no per-position work.
- **Volet 1 — diagnostics at the use site.** Member absent from the target module → `E0104 UnknownExport`; member present but `.private` → `E0107 ImportPrivateItem`; these reuse the export-lookup + visibility branch of `bindImports` selective handling. Unlike the selective form (which names members at the `import { … }` binding and diagnoses there), the whole-module import names no members, so `E0104`/`E0107` fire at the **use site** (`type X = m.Nope`). A receiver ident that is not a whole-module alias (a local, a param, a selective-imported symbol) falls through to existing resolution unchanged — no regression; `E0102 UndefinedSymbol` for a genuinely unresolved receiver.
- **Volet 2 — `private` visibility inheritance (§10.2).** The `impl` and methods of a `private` type inherit the type's visibility (implicitly private): the resolver does not surface a private type's methods as exported/public. Cross-module access already fails (the private type is unnameable); this ensures no path leaks it as public.
- **Volet 2 — `W0902 PrivateTypeInPublicImpl`.** New warning: `impl PublicTrait for PrivateType` (target type `private`, trait public/imported) emits `W0902` (warning, not error — legitimate for internal use). Detection iterates `impl_decls` with `trait_name != 0`, checking the target type's visibility (private) and the trait's visibility (public). New code in `diagnostics.zig` (`W0902`, spec-assigned by `etch-resolver-types.md §10.2` and `etch-diagnostics.md §21.1`).
- **Acceptance corpus.** Zig driver tests under `validateProject` over multi-file `ProjectFile` fixtures (the `tests/etch/import_resolve_test.zig` pattern), mirroring the M1.0.7 selective tests with `as m` + `m.Type`.
- **KB reconciliation (Step 4, complete re-uploadable files by Claude.ai).** `etch-grammar.md` gains the `qualified_path` production (type position). `etch-resolver-types.md §3.3` refines `resolve_path` to distinguish absent (`E0104`) from present-but-private (`E0107`), and §3.1 notes the grammar production now exists for the alias-qualified (single-step) form. `etch-diagnostics.md §25` adds `W0902` to the Phase 1 coverage list.

## Out of scope

- **Expression-position qualified access** — `m.Type { … }` (qualified struct literal), `m.func()` (qualified free-function call), `m.Type.CONST` (qualified associated access). Not a proven capability of the selective form (its twins `Type { … }` / `func()` from a selective import do not resolve today either). Making them work is a separate "import usability in value positions" concern that must first fix the selective form; it is not "qualified imports." Explicitly refused for this milestone, not deferred debt.
- **Using an imported type directly as a component field type** and the associated POD boundary — a pre-existing limitation shared by the selective form (a component is not a valid field type anywhere; imported-type field-position behavior is whatever the selective form already does). Not touched, not extended here.
- **Uppercase associated access `Type.CONST`** (e.g. `Vec3.UP`) — a separate latent grammar gap (`TYPE_IDENT . TYPE_IDENT` postfix), unrelated to module aliases.
- **Multi-segment module sub-paths** (`m.sub.Type`). Etch modules are flat files; alias-qualified access is a single `alias . member` step.
- **Broader `private_in_public`** (a private type in any public field / param / return, Rust-style). Ruled out for v0.6 (decided with Guy: §10.2 literal). `W0902` on trait impls is the spec's mechanism for the criterion.
- **`W0901 UnusedThrowsDeclaration` / `W0903 DeprecatedItem`** — other W09xx codes; not this milestone.
- **The LR(1) grammar generator / DSL** (`src/etch/parser/grammar/`, `tools/etch_lr_gen`, `zig build parser-gen`, `tests/grammar_consistency.zig`) — the planned parser architecture (`etch-parser.md §4`), not present at this tag. The parser is the hand-written `src/etch/parser.zig` (recursive descent + Pratt). The grammar change is EBNF (`etch-grammar.md`) + hand-edit of `parser.zig`; do not scaffold the generator.

## Notes

**Gate breakdown (E1–E2, gate-by-gate review protocol):**

- **E1 — Qualified type-name parse + resolution.** In-repo recon first (mandatory, journaled): (a) the `.path` TypeNode slab shape following `NamedTypeNode`; (b) confirm the three `imported_symbols` consult sites (`namedTypeToResolved`, `validateTypeAliases`, `checkComponentInstance`) are the exact parity surface, and how an `imported_aliases` target file index reaches `project.exports[idx]` from each; (c) confirm `E0104`/`E0107` must fire at the use site for the whole-module form (the import binding names no members); (d) the receiver-disambiguation order so a whole-module alias never shadows a legitimate local/param/selective-symbol receiver. Then: EBNF `qualified_path` (type position), `.path` TypeNode in `ast.zig`, `parseBaseType`, and the three consult sites consuming `imported_aliases` with `E0104` / `E0107` / `E0102`.
- **E2 — `private` completion (§10.2).** Visibility inheritance (a private type's `impl`/methods not surfaced as public) + `W0902 PrivateTypeInPublicImpl` over `impl_decls` (trait impl, private target type, public trait). Add `W0902` to `diagnostics.zig`.

**Traps and constraints:**

- **Parity is the scope boundary.** Qualified `m.Type` resolves exactly where selective `Type` resolves, by sharing the same consult sites. Do not extend resolution to positions the selective form does not already cover (expression struct literals, free-fn calls, field-of-component POD) — those are pre-existing whole-import limitations, out of scope.
- **Diagnostic timing.** For the whole-module form, `E0104`/`E0107` fire at the qualified use site (`m.Nope`), not at the `import` binding. The check reads the target module's `project.exports` entry (`buildExports` records private entries with `visibility == .private`) — same data the selective branch reads. Do not mint a code for `E0104`/`E0107`. `W0902` is the only new code, spec-assigned.
- **Multi-file test vehicle.** Qualified imports require a project: `bindImports` is a no-op when `project == null`. Tests build a `ProjectFile` set and call `validateProject` (the `import_resolve_test.zig` pattern). The `etch_test` single-file shim cannot exercise this.
- **No parser generator at this tag.** The parser is hand-written `src/etch/parser.zig` (RD + Pratt). The grammar change is EBNF (`etch-grammar.md`) + hand-edits to `parser.zig`. Do not scaffold `src/etch/parser/grammar/` or `tools/etch_lr_gen`.
- **Receiver disambiguation (no regression).** Qualified resolution fires only when the receiver ident is a whole-module alias in `imported_aliases` and is not shadowed by a local in scope. Existing field/enum/associated accesses on non-alias receivers must resolve exactly as before.
- **String discipline (M1.0.14/15 lesson).** Resolution operates on interned `StringId`s and export entries, not heap `Value`s, so the UAF surface is minimal — but any name/message copied into a diagnostic that outlives interpreter scratch memory goes through the `stringNeedsOwning` / deep-copy discipline.
- **Module rooting (Zig 0.16 lazy analysis).** `tests/etch/qualified_import_test.zig` must be transitively reachable from its test root or its `test` blocks silently skip (cf. `engine-zig-conventions.md §13`). Verify real execution, not mere presence.

**Rejected alternatives (recorded):**

- **Anchoring acceptance on field-type / struct-literal / free-fn positions** (the initial brief draft): rejected after E1-recon parity analysis — the selective form does not resolve imports in those positions today, so asserting them for qualified access is an out-of-parity scope expansion (the `component`-as-field POD rejection and the "not a struct type" struct-literal rejection are pre-existing and orthogonal). Acceptance is anchored on the type-alias target, the one proven selective-resolution position (M1.0.7).
- **Extending resolution to expression-position qualified access**: rejected — a separate "import usability in value positions" concern that must first lift the selective form's limitation. Not qualified-imports work.
- **Minting a dedicated qualified-path node**: rejected — the reserved `.path` TypeNode is exactly for this; used as-is.
- **Broadening §10.2 to full `private_in_public`**: rejected for v0.6 — `W0902` on trait impls is the spec's mechanism.
