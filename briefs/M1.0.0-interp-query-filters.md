## Context

M0.8 delivered the tree-walking interpreter over the full v0.6 grammar (three levels) with a working dynamic ECS bridge (runtime component registry, dynamic SoA archetype, resource store). At S4/M0.8, the interpreter walks `world.archetypes` directly; the M0.8 debt work added multi-`has_with_filter` per rule and an `or`-predicate bitset short-cut. Tier-0 ECS (M0.1) provides archetype-level filtered queries. The resolver already compiles each rule's `when` clause into a static `archetype_set` and an `ECSAccessMap` (`etch-resolver-types.md §12.2`).

This sub-milestone wires the interpreter's per-rule entity selection to that precomputed `archetype_set`, so a rule's `when` clause filters entities by archetype: presence (`has`), exclusion (`not has`), value field-filter (`has T { field op value }`), and full `and`/`or`/`not` composition. It is pure interpreter-side capability — no grammar and no resolver change. It is the first Phase 1 prerequisite for piloting any module from Etch.

- Etch test cases under `tests/etch/v1/` covering each filter form and composition.

## Acceptance criteria

### Tests

- `tests/etch/v1/` — `test "filter has only"` — a rule with `when entity has T` visits exactly the entities whose archetype contains `T`, none other.
- `tests/etch/v1/` — `test "filter not has"` — `when entity has A and not entity has B` excludes entities carrying `B`.
- `tests/etch/v1/` — `test "field filter eq"` — `when entity has T { field == value }` visits only entities whose `T.field` equals `value`.
- `tests/etch/v1/` — `test "field filter ordered"` — a `>` (or `<`) field-filter case visits only matching entities.

## Notes

- The plan title uses the Tier-0 nomenclature `With<T>`/`Without<T>`. There is **no** such surface in Etch — filtering is expressed through the `when` clause (`has` / `not has` / `has T { … }`). Do not introduce a turbofish-style filter syntax.
- The resolver is authoritative for archetype matching and access tracking; the interpreter consumes its outputs. If the audit shows the interpreter recomputing matching independently of `archetype_set`, converge it onto the resolver output rather than duplicating logic.
- M0.8 already addressed the single→multi `has_with_filter` per rule and the `or` bitset short-cut debts. Confirm their exact current behaviour at Livrable 0 before extending; do not regress them.
- `RuntimeQuery` / `world.query_dynamic` were left unused on the hot path as an S4 debt (interpreter walks `world.archetypes` directly). If routing selection through `archetype_set` makes `RuntimeQuery` the natural carrier, wiring it in is in-scope; dropping it cleanly is also acceptable. Record the choice as an acted deviation if it changes the public bridge surface.

## Acted deviations

### AD-1 — `archetype_set` matérialisé côté interpréteur (pinned au Livrable 0)

Le brief (Context FROZEN) suppose un `archetype_set` précalculé par le resolver,
consommé tel quel par l'interpréteur. L'audit montre qu'aucun `archetype_set`
n'existe côté resolver (`types.zig` ne trace que `components_in_when`, « no
archetype query is derived ») et que modifier le resolver est hors-scope. Sous
l'autorité explicite des notes 95 et 97 du brief et du mandat Livrable 0
(« exact symbol surface pinned at Livrable 0 »), l'`archetype_set` est
matérialisé côté interpréteur : le set d'archétypes matchants caché par règle
(`RuleDesc.matching_archetypes`, rescan lazy `Query.maybeRescan`), généralisé
de « règles `or` au-dessus du seuil 8 » à **toutes** les règles entity-bound.
Aucune modif resolver/grammar/lexer/parser. Le bridge (`ecs_bridge.zig`) ne
porte pas la sélection — l'édition de sélection vit dans `interp.zig`.
**Surface publique du bridge inchangée** (note 97). Décision tranchée sur la
base du brief lui-même, signalée à Guy dans la réponse de session.
