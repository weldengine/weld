## Context

This milestone extends the Etch S3/S4/S5 subset to the **full EBNF v0.6 grammar** and advances criterion **C0.2** (Etch usable end-to-end). The parser stays **recursive-descent + Pratt**; the hybrid LR(1) incremental rewrite is Phase 1 (C1.11, `etch-parser.md §23`) and is out of scope. This is the largest Phase 0 milestone — it is delivered in **seven reviewed stages (E1–E7)**, each landing a testable vertical slice, on the M0.5/M0.6/M0.7 model.

**What S3/S4/S5 actually delivered (verify in code before scoping each stage).** The S3 subset is narrow: `component`, `resource`, `rule`, the `when` clause, and basic arithmetic expressions only. The infrastructure delivered is reusable as-is and is what this milestone *extends*: a UTF-8 lexer, a tabular SoA AST (`MultiArrayList(Item|Stmt|Expr|TypeNode)`), a two-pass type-checker, typed diagnostics (`src/etch/`, ~2050 lines, public API in `src/etch/root.zig`), a tree-walking interpreter with a dynamic ECS bridge (runtime component registry, dynamic SoA archetype, resource store), and a **direct AST→Zig codegen with no HIR** (`comptime_query.query(world, .{T...})`, one non-generic function per rule, `Registry.registerAlias`). **`fn`, `struct`, `enum`, `trait`, `impl`, `event`, `tags` are NOT in the delivered subset — they are net-new construct support in this milestone, not completion of existing code.** The "extension" is of the *infrastructure*; most constructs themselves are new. Claude Code confirms the delivered surface (read `src/etch/root.zig` + the S3/S4/S5 corpus) before scoping each stage; it does not re-spec from this brief what already exists.

**Three construct support levels (governing distinction — do not collapse it).** The plan says "interpreter executes all constructs", which is unrealistic as stated: real Tier 1 modules (Cortex, UI/Islandz, Kinesis, Pulse, Ember, Sequencer, Render) are out of Phase 0 scope beyond their interface stub. One cannot *execute* an `audio_graph` or an `anim_graph` without an audio/animation engine behind it. The dependency of Level B constructs on Tier 1 modules is a deliberate architectural property, not a gap. Hence three levels:

- **Level A — real behavioural execution.** `fn`, `component`, `resource`, `event`, `rule`, `tags`, control flow, expressions. The interpreter genuinely executes against the mini-ECS; the codegen emits functional Zig; **the byte-exact differential is the world state after N ticks.**
- **Level B — declaration + internal IR/descriptor, no module wiring.** `behavior`, `routine`, `quest`, `dialogue`, `ability`, `data`, `widget`, `theme`, `motion`, `locale`, `input_mapping`, `shader`, `effect`, `anim_graph`, `audio_graph`, `audio_score`, `sequence`. Full sub-grammar parse + semantic validation + structure construction. The differential is on the **serialized internal IR/descriptor**, not on absent module behaviour.
- **Level C — serialization.** `scene`, `prefab`. Parse + typed extensions (`.scene.etch` / `.prefab.etch`, `E0858`) + validation. Runtime instantiation is M0.9 (`engine-scene-serialization.md`), not this milestone.

Consequence for the 500-line reference differential: the file is built so the diffed observable behaviour comes from **Level A** (rules/events/ECS state). Level B/C constructs appear in it to validate parse + codegen-compiles, not for a behavioural diff.

## Scope

The work is delivered as **seven vertical stages** (parser→interpreter→codegen per construct group), in dependency order. Each stage lands a testable slice and ends with a review gate (`Review Ei`): Claude Code completes the stage, pushes, and waits for a Claude.ai review relayed by Guy before starting the next stage. The stage decomposition is the work breakdown for Step 3 of the execution protocol; it is not a re-scope mechanism and Claude Code never re-cuts it mid-milestone.

**Execution grain inside a stage (fixed — do not ask how to sequence it).** Claude Code implements the entire `Ei` block in a single pass, then stops at the `Review Ei` gate and presents the stage diff. There is no per-construct sub-decomposition and no intra-stage checkpoint: a stage is reviewed once, at its end, on its differential — not feature by feature. Claude Code does not ask Guy how to run a stage; the grain is settled here.

**E1 — Language foundations (non-ECS) + 5 S3 debts + breaking interface + EBNF harness mechanism**
- v0.6 expression/control-flow foundations: exhaustive tiered `match` (Maranget algorithm), closures `|a| e`, `loop` / labeled loops / `break label value`, ranges `..=`, collections `T[N]` / `T[]` / `Map` / `Set` / `Iterator`, casts `as`, error handling `throws` / `throw` / `try` / `catch` / `assert`, `type` aliases. Exercised inside `rule` bodies (delivered at S3). Full stack: parse + interpret + codegen.
- The 5 S3 debts (all lexer/parser/resolver core): **D-S3-trivia** (trivia/doc comments attached to nodes via `TriviaMap`); **D-S3-doccomment** (`///` lexed as doc comment, not line comment); **D-S3-annot-applicability** (annotation applicability validated, cf. `etch-resolver-types.md §13`); **D-S3-annot-field-access** (`@requires(self.health)` parses, fix `continuePostfixAndBinary` → `parsePostfix`); **D-S3-resource-receiver** (`get(T)` / `get_mut(T)` resources without receiver supported in rule body).
- Breaking interface change: `ParseResult.diagnostic: ?Diagnostic` → `diagnostics: []Diagnostic`, plus the top-level recovery sync-point (after a diagnostic, advance to the next top-level keyword or EOF, then resume `parseTopLevel`). Landed here because every later stage consumes this interface.
- EBNF harness mechanism: the `@embedFile` + feed-to-parser machinery for `ebnf_examples_test.zig`, then fed continuously as constructs land.
- **Review E1:** foundations differential (expressions, `match`, closures, error handling) + recovery sync-point test + the 5 S3 debts each with a test.

**E2 — Type-declaration layer (Level A)**
- `fn` (top-level + associated), `struct`, `enum`, `trait`, `impl`. Net-new (the S3 subset lacks them — verify, do not re-spec the existing). Full stack: parse + interpret + codegen.
- Generic syntax `<T>` is **parsed** and **interpreted** (the tree-walker monomorphises at runtime trivially). **Generic codegen monomorphisation is out of scope** (HIR-dependent, Phase 2 — see Out-of-scope). `async fn` syntax is **parsed** here; its interpretation and codegen boundary are set in E3.
- **Review E2:** differential on `fn` / `struct` / `enum` / `trait` / `impl` behaviour; generic instances validated through the interpreter only.

**E3 — Executable ECS layer (Level A complete) + 5 S4 debts + 2 S5 build debts**
- `event` declarations + observers + ECS event bridge.
- `tags` hierarchical declaration: compact bitfield encoding (`etch-validation-ecs.md §5`), operators `has_tag` / `has_no_tag` / `has_any_tag` / `has_all_tags` / `has_no_tags`, `add_tag()` / `remove_tag()` deferred structural mutations at the tick boundary.
- `rule` extended to complex queries with `With<T>` / `Without<T>` / `Changed<T>` filters (`etch-validation-ecs.md §12`).
- Async **interpretation** (the tree-walker is its own runtime: suspend on `await`, resume on wake). Async **codegen is out of scope** (see Out-of-scope).
- Absorb the 5 S4 debts: **D-S4-runtime-query** (`RuntimeQuery` / `world.query_dynamic` consumed on the interpreter hot path, or the abstraction dropped); **D-S4-runtime-report** (`RuntimeReport.last_error` assigned by `execBody`, typed `RuntimeError`/`SourceSpan` propagated to the caller); **D-S4-ecs-bridge-panic** (`ecs_bridge.writeValueAsBytes` returns a `TypeMismatch` variant instead of `@panic`); **D-S4-or-archetype** (`or` predicate gets a bitset short-cut above an archetype-count heuristic); **D-S4-multifilter** (per-rule field filter supports several `has_with_filter` — array, not single).
- Absorb the 2 S5 build debts: **D-S5-etchcook-inproc** (`etch_cook` consumed as an in-process build helper, not a subprocess); **D-S5-synth100-proper** (`synth_100/build.zig` is a proper sub-project depending on `weld_core`, not a placeholder).
- **Review E3:** byte-exact ECS differential (events, observers, filtered queries, tags) + the 7 debts each with a test. **End of E3 = Level A complete in both interpreter and codegen** (async excluded from codegen).

**E4 — Level B gameplay** (6 constructs)
- `behavior`, `routine`, `quest`, `dialogue`, `ability`, `data`: exhaustive sub-grammar parse + semantic validation (`etch-validation-ecs.md`, relevant gameplay sections) + internal IR/descriptor + interpreter builds the structure + codegen emits the Zig structure.
- **Review E4:** internal-IR differential.

**E5 — Level B presentation** (5 constructs)
- `widget`, `theme`, `motion`, `locale`, `input_mapping`: exhaustive parse + validation (`etch-validation-ecs.md`, UI + input sections) + internal IR + interpreter/codegen structure. `input_mapping` is Level B strict: parse + validation + IR, **no input execution**.
- **Review E5:** internal-IR differential.

**E6 — Level B render / animation / audio / cinematic** (6 constructs)
- `shader`, `effect`, `anim_graph`, `audio_graph`, `audio_score`, `sequence`: exhaustive parse + validation (`etch-validation-ecs.md`, render/anim/audio sections) + internal IR + interpreter/codegen structure. `shader` includes the resolver's shader mode (rejects heap/string/Entity/closures/async). SPIR-V/MSL/DXIL/WGSL emission is out of scope (Phase 2+).

**E7 — Level C + closure**

## Out-of-scope

- **Hybrid LR(1) + Pratt parser** — Phase 1 / C1.11 (`etch-parser.md §23`). The parser stays recursive-descent + Pratt.
- **Async codegen to Zig** (state-machine / CPS lowering of `async` / `await` / `race` / `sync` / `branch` / `spawn`). Zig 0.16 has no language-level `async`, so this needs a hand-emitted state machine + task runtime; the spec wants that desugaring factored through the HIR (`etch-ast-ir.md §5.3, §9.4, §11`), and the M0.8 codegen is the direct AST→Zig path with no HIR. Phase 2 per `etch-ast-ir.md §11`. Async is parsed (E2/E3) and interpreted (E3) only.
- **Generic monomorphisation codegen** — same root cause as async (HIR-dependent lowering not present in the direct AST→Zig path). Phase 2 per `etch-ast-ir.md §11`. Generics are parsed and interpreted (E2) only.
- **VM bytecode** (`.etchc`) — Phase 2 (`etch-bytecode.md`).
- **Shader backend codegen** (SPIR-V / MSL / DXIL / WGSL via AIR) — Phase 2+. E6 delivers shader parse + resolver shader-mode validation only.
- **Highlighting / folding / structural-selection visitors** — Phase 2 (`etch-parser.md §14`).
- **Full recovery cascade** (virtual tokens, panic-mode, fine sync points) — Phase 1 / S2+. E1 delivers top-level resync only.
- **Separate CST** — Phase 1 / S0 (`etch-parser.md §10.1`).
- **Runtime execution / wiring of any Level B construct against a real Tier 1 module** (Cortex, UI/Islandz, Kinesis, Pulse, Ember, Sequencer, Render). Level B is declaration + IR only in Phase 0.

## Notes

- **A/B/C levels rationale.** Level B constructs depend on real Tier 1 modules (Cortex, UI/Islandz, Kinesis, Pulse, Ember, Sequencer, Render), which are out of Phase 0 scope beyond their interface stub. They are therefore declaration + internal IR/descriptor only in this milestone; their runtime wiring is post-Phase-0. This is deliberate, not a gap.
- **Async + generics codegen deferral.** Both are HIR-dependent lowerings (async = state machine / CPS; generics = monomorphisation) that the spec factors through the HIR (`etch-ast-ir.md §5.3, §11`). The M0.8 codegen is the direct AST→Zig path delivered at S5, with no HIR. Both are parsed and interpreted in M0.8; their Zig codegen is Phase 2 per `etch-ast-ir.md §11`. This is the boundary of the plan's "implementable shipping-side" codegen clause.
- **Sensitive criterion.** Incremental compile < 2 s had ~1.9× margin at S5 (the only tight Phase −1 gate). Extended codegen risks eroding it; treat it as a monitored gate, not a safe non-regression.
- **Scope clarification (Claude.ai decision relayed by Guy, 2026-06-06).** for-in + collection indexing/slicing confirmed in E1 as the entailed consumers of the scoped ranges/collections; not a scope expansion. Rationale: a collection without indexing/slicing is unusable, an `Iterator` without for-in is unusable, a range without for-in is inert — so `for ... in`, `arr[i]`, and `arr[0..3]` are not new scope but the consumers the scoped `ranges`/`collections` lines already entail. They are implemented together so each feature has a real differential (`for i in 0..10 { sum += i }`, `arr[i]`, `arr[0..3]`). Anti-hallucination: these forms are implemented strictly from `etch-grammar.md` (`for_stmt` §line 621, `range_expr` §410-411, `postfix_op "[" expression "]"` §425) + `etch-reference-part1.md` (§6.5 ranges, §7.3 for-in, §11 collections) — verified present before writing.
- **Two documentation drifts (out of scope here; patch at M0.8 close, not mid-milestone).** (1) `engine-phase-0-plan.md §M0.8` says "11 debts" but lists 12 (5×D-S3 + 5×D-S4 + 2×D-S5) — it is **12**; the "11" is a typo. (2) `etch-ast-ir.md §11` uses the pre-renumbering Phase 0.5/1/2 labels and an HIR-centric model out of sync with the direct AST→Zig codegen delivered at S5; the relative ordering (async/generics codegen after the basics) is correct, only the phase labels are stale. Both are KB realignments for the plan-close patch (delete-and-reupload), neither touches M0.8 code.
