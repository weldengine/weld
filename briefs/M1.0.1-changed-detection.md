## Context

The `entity has T changed` per-tick change-detection mechanism was delivered by M0.8 (E3) and preserved unchanged by M1.0.0. This milestone does NOT reimplement it. It closes the test debt around that mechanism as exposed to the tree-walking interpreter: the single existing test proves only inter-archetype granularity, and a test-runner coverage gap (a M1.0.0 finding) means a class of `src/etch` inline tests — including the file where this milestone's tests live — may not execute under `zig build test`. The milestone's capability is a trustworthy, executed proof that a `changed` rule fires exactly on the entities modified this tick, down to the per-slot level inside one archetype.

## Scope

- Wire the interpreter test files (`src/etch/interp.zig`, plus `src/etch/value.zig` and `src/etch/ecs_bridge.zig`) into the etch test root so their inline tests are actually collected and executed by `zig build test`. Bring every test surfaced by this wiring to green (fix-as-you-go); do not leave any wired-in test red, and do not leave a file uncollected to avoid surfacing its reds.
- Audit the etch test step's collected-test count and reconcile it against the `src/etch` inline-test population (perimeter below), so the set of files NOT reached from the test root is established by measurement, not enumeration. Confirm `src/etch/parser.zig` coverage status as part of this count audit (the M1.0.0 finding flagged it specifically).
- Add an inline interpreter test proving per-slot **intra-archetype** granularity: two entities in the SAME archetype, only one selectively modified this tick → a `changed` rule fires only for the modified entity.
- Add the same per-slot scenario as a `.etch` fixture under `tests/etch/v1/`, following that directory's existing fixture convention.
- Add inline interpreter tests for three `changed` edge cases: (a) a `changed` filter combined with a field-filter on the same rule; (b) a `changed` filter across an archetype migration, proving the `changed_tick` travels with the entity; (c) a `changed` filter on a freshly-spawned entity, proving the spawn-tick stamp is observed.

## Acceptance criteria

### Tests

- `src/etch/interp.zig` — `test "runProgram changed fires per-slot intra-archetype (M1.0.1)"` — two entities in one archetype, one component selectively written this tick; the `changed` rule's effect is observed on the modified entity only.
- `src/etch/interp.zig` — `test "runProgram changed combined with a field-filter (M1.0.1)"` — a rule carrying both a `changed` filter and a field-filter fires only when both hold.
- `src/etch/interp.zig` — `test "runProgram changed_tick travels across archetype migration (M1.0.1)"` — an entity migrated to another archetype retains its `changed_tick`; the `changed` rule behaves accordingly across the migration boundary.

## Notes

- The mechanism is implemented and must only be OBSERVED by the new tests, never re-added. For orientation when writing tests: rule-level `changed_filters` + `last_run_tick` and the `has_changed` gate live in `interp.zig`; the per-write stamp is `markComponentChanged` in `ecs_bridge.zig`; the `changedTick` / `markChanged` accessors and the tick sidecars live in `archetype.zig`; migration preservation (surviving columns carry their pre-migration `changed_tick`) is in `world.zig`'s dynamic add/remove-component paths; the spawn-tick stamp is applied when a slot is allocated at `World.current_tick`. Tests assert this existing behavior.
- The existing test "runProgram `has T changed` gates a rule on per-tick change detection (M0.8 E3)" proves only INTER-archetype granularity: its two entities sit in different archetypes (one carries an extra marker component, one does not). The new per-slot test must place both entities in the SAME archetype and differentiate them by a selective write, which is the case that test does not cover.
- On the wire-in: per `engine-zig-conventions.md §13`, a file imported into `root.zig` whose declarations are not actually exercised by analyzed code (including `root.zig`'s own tests) can have its inline tests skipped. `interp.zig` is re-exported as a type alias but is never called from `root.zig`, which is the suspected cause; the count audit confirms the exact set. The fix is the same reference-guard idiom already used in `zig_codegen/root.zig`.
- If any test surfaced by the wiring fails only in the combined run but passes in isolation (`--test-filter`), it is order-dependent on shared mutable state. Neutralize the shared state at its source; do not mask it by reordering or by gating the test out.
- A `readCounterValue` helper already exists in `interp.zig` for reading a component field from a test; reuse it rather than duplicating field-read plumbing.
- Recommended (not a hard criterion): consider a lightweight regression guard so the collection gap cannot silently reappear. Do not invent a heavy build mechanism for it; if a clean guard is not obvious, leave it as a tracked note rather than expanding scope.
- The `zig_codegen/**` test-collection gap is real but belongs to a separate (Phase-2 codegen) perimeter. It is to be given a named home with a milestone assignment in the Phase-1 plan (a KB action, outside this branch). Do not address it here.
