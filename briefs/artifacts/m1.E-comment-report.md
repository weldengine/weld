**Reading this report, not the diff, is how the pass is reviewed.** A diff of
thousands of removed comment lines is unreadable. What is reviewable is, per file,
the count before, the count after, and — for the files where the criterion made a
judgement call — what was kept and why.

## The measurement, and its definition

A **comment line** is a line whose first non-blank token is `//`. A **code line** is
any other non-blank line. Blank lines are in neither term, and a trailing comment is
part of its code line. The density is `comment / (comment + code)`, and the ceiling
is **25 %** — a house rule, written down, not derived from the result of this pass.

That definition was not chosen, it was **identified by measurement**. Four candidate
denominators were computed over `src/`; only this one reproduces the recorded
baseline to the digit. `comment / total_lines` gives 26.76 % on the same tree, so a
report written on it would be measuring a different quantity under the same name.

**Two independently written implementations agree on every figure below** — the Zig
rule that will enforce the ceiling, and a Python probe written before it from the
definition alone. Agreement of two computations of one quantity is what authorises
the number; a single instrument agreeing with itself would not.

**The minimum-to-remove figure is a lower bound on removal, not an estimate of the
work.** Removing a comment line shrinks the denominator as well as the numerator, so
a file may keep one comment line per three lines of code; the naive excess over 25 %
of the current total understates it by a third. The conservation criterion may remove
more than the bound, and a file whose every survivor meets the criterion takes an
allowlist entry instead of a further cut.
