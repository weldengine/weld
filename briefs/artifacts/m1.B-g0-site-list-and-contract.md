### 1.6 The zero-sized component precedent exists — this author's first measurement was wrong

A grep for `.size = 0` returned nothing outside `src/core/ipc/`, and for
`component X {}` in the Etch corpora nothing at all, from which this author first concluded
that invariant 5 had *no table-side precedent to mirror*. **That is refuted.**

`src/modules/forge/api/components.zig:36` declares `pub const Sleeping = extern struct {};`
— a zero-size POD marker, registered through `Registry.registerComponent(T)` with

`"Sleeping is a zero-size POD marker"` (265) asserting `@sizeOf == 0` and zero fields, and
`"Sleeping survives registration, spawn, add and remove in a real World"` (274).

a **paired twin** to mirror rather than a blank page. The grep was the wrong instrument for

*audit the wiring, not the result*
(`engine-development-workflow.md` §5.5, § *Surface et conception*).

What remains true and narrower: **no Etch-declared empty component exists anywhere in the
corpora**, so the `@storage(sparse) component InCombat {}` shape of the spec's own example is
unexercised end to end today. `Archetype.init` refuses an empty component **list**
(`ArchetypeError.EmptyComponentList`, line 164) and nothing refuses a zero **size**.

## 2. The contract

Written from §1. It quantifies where it must cover sites that do not exist yet, and it states
what does not move as explicitly as what does.

### 2.1 The mode is a runtime-registry property with exactly one producer

`StorageKind = table | sparse`, default `table`, owned by `engine-ecs-internals.md` §2. The
mode is recorded once, at component registration, in the runtime registry — never in on-disk
identity (`engine-scene-serialization.md` §4), never in a chunk, never on an archetype.

**The mode has exactly one producer: the resolved `@storage` annotation on an Etch
`component` declaration.** Any second producer is a change of contract, not an
implementation detail. In particular a Zig-declared component reaches no annotation and is
therefore `table` by construction — which is what bounds §1.15 (see §3.1).

### 2.2 The obligation is on the site, quantified — not on a list

> **Any site that resolves, mutates, enumerates or tests an `(entity, component)` pair must
> reach its answer through a mode-routing entry, and failing to is a defect of that site.**

The list in §1 is the set of such sites *at `3fd5472`*. It is not the rule. A site added later
that answers such a question without routing is a defect of that site whether or not this
document enumerated it.

Three consequences the enumeration makes concrete:

- **The four funnel entries route.** `get`, `getMut` (with its auto-mark), `componentBytes`,
  `markComponentChangedDyn`. `markComponentChangedDyn`'s missing liveness gate is preserved
  as-is on the table arm and **matched** on the sparse arm — the asymmetry is inherited, not
  re-decided, and the contract says so rather than leaving a reader to infer a decision.
- **The fifth path is a routing hole by construction, and the answer is a locator, not a
  patch.** `dynamicLocation` + `dynamicArchetype` hand out a triple that a sparse row cannot
  produce. 27 production sites consume it. The obligation is to give those sites a
  **storage-agnostic locator** — the shape `value.ResourceRef` already has (keyed by id, no
  chunk, no slot) — and to leave the triple available for the table arm.
- **Membership becomes a first-class entry.** A `World`-level per-entity membership test is
  required by the planner and does not exist. Its semantics are already frozen elsewhere under
  the name `component_has` (`plugin_loader/api.zig:222`); the Tier-0 entry matches those
  semantics so the two never diverge.

### 2.3 The partition happens before the signature, at six sites

A sparse component id **never enters an archetype signature**. Concretely: the table/sparse
split is applied before `archetype.sortComponentIds` at each of `world.zig:593, 632, 667, 841,
929, 1079`, and `archetype.signatureBytes` is computed over table ids only.

The consequences are the point of the mode and are stated positively:
- two entities differing only in sparse components share one archetype;
- a sparse add or remove creates **no** archetype transition, so `TransitionCache`
  (`archetype.zig:81`) is neither consulted nor populated on that path;
- an entity whose entire component set is sparse still needs an archetype, and
  `Archetype.init` refuses an empty list — so the empty-signature case is a decision this
  milestone owes, not a case it may leave to a panic.

### 2.4 Both directions of every apply path, and the count is three

All three switches of §1.4 route: `CommandBuffer.applyOne`, `applyWithObservers`,
`applyRawCommand`. A property asserted on one and not the others is the milestone's dominant
defect shape, so the oracle **enumerates the kinds covered per switch and reports the count**
— per `engine-development-workflow.md` §5.5, a probe that returns a verdict returns the size
of what it judged.

The `else`-free exhaustiveness of the three switches protects a *new kind* and protects
nothing about a *new route inside an existing arm*; the contract does not borrow credit from
it.

### 2.5 What does not move

Stated because §1's own silences are where an implementer fills in the available fact — the
failure mode `engine-corpus-map.md` anomaly 83 records.

- **An all-table query takes the delivered path, unchanged.** `Query`, `DynamicQuery`,
  `archetypeMatches`, `rescanNewArchetypes` keep their behaviour bit for bit; the check states
  which path was taken rather than inferring it from the result.
- **`beginFrame` clears chunk dirty bitsets and a sparse store has none** (invariant 2). It
  iterates `self.archetypes.items`, which no sparse store joins. **`beginFrame` therefore
  needs no sparse arm**, and that is a conclusion, not an omission. `tickBoundary` touches
  resource dirty bits only and is off the storage path entirely.
- **The scene and prefab codec is not reopened.** The loader instantiates entity by entity —
  a single `spawnDynamicWithValues` at `loader.zig:453` inside `instantiate` (387) — so the
  bifurcation is wholly inside the spawn path. `buildSchemaRemap` (123) keeps comparing name,
  size and alignment. **The cook's grouping by full signature (`scene_cook.zig:1108`) does not
  change**: two blocks whose table subset coincides instantiate into one archetype, so the
  merge is acquired at load and no re-cook is owed.
- **The eight determinism witnesses cannot move through the ECS, structurally.**
  `src/modules/forge/forge_3d/` imports `weld_core` in **zero** files, and
  `determinism_main.zig` imports only `std`, `builtin`, `foundation` and its own module files.
  The scenario owns a `PhysicsWorld`, not a `World`. A red witness on this milestone would
  therefore indicate something other than a storage change — which is what makes it a defect
  to isolate rather than a regeneration to declare.
- **`WELD_ECS_PROTOCOL_VERSION` stays 1**, and the check enumerates the surface it inspected
  and reports its size, per the brief.
- **`added_tick` gains no consumer.** The change filter becomes storage-agnostic; nothing
  starts reading the added sidecar.

### 2.6 What the rule does not cover, and why

- **It does not govern the C plugin ABI.** `component_register` cannot carry a mode and
  `WeldQueryChunk` cannot express a dense range. Both are frozen under `ARCH-018`, both are
  stubbed, and `ARCH-019` makes a Tier 3 backend non-loadable before Phase 3. The ABI is
  therefore out of the rule's domain **today**, and the day it enters, `ARCH-018`'s
  end-of-struct append with a minor bump is the mechanism — not a redesign.
- **It does not govern resource types.** `@storage` applies to `component_decl`, so no
  resource can be sparse, and the `[T, ResourceMarker]` distinctness argument
  (`resources/registry.zig:84-87`) is untouched. Naming this matters because the argument is
  stated in signature terms and §2.3 removes ids from signatures: the two would collide if the
  domain were ever widened.
- **It does not govern the codegen's query engine.** `comptime_query.zig` sees only table
  components because the codegen **refuses** any program exercising a sparse one. The refusal
  is the deliverable; parity is Phase 2-3. `comptime_query.zig` therefore needs no change, and
  that is a decision recorded here rather than a file quietly left out.
- **It does not make a `.sav` or `.scene.bin` schema check sensitive to a size-preserving
  field addition.** That blind spot is independent of this milestone
  (`engine-scene-serialization.md` §4) and nothing here adds a field inside existing padding.

### 2.7 The seven backend invariants, each with its opposable form

Transcribed from `engine-ecs-internals.md` §2 with the shape each proof takes, per
`engine-development-workflow.md` §5.5 — *an oracle is confronted with a change of the object,
never of its own constant.*

| # | Invariant | Opposable by |
|---|---|---|
| 1 | swap-remove parity of the tick sidecars | a **relocation**: remove a non-last entry, then assert a change filter sees the relocated entity exactly as it would have seen it un-relocated |
| 2 | no bitset, so no block skip | the absence of any per-block skip on the sparse path, with its positive witness — the table path's skip still fires |
| 3 | despawn purges every storage | no sparse index entry designates the dead entity, **and** a re-spawn at the same index with a new generation does not inherit the component |
| 4 | observer firing order at despawn | ascending `ComponentId` over the **union**; counter-factual = permuting the components' declaration order changes nothing |
| 5 | zero-sized components | paired with its table twin, `components.zig:274` — added, tested, removed, with no component array allocated and no pointer derived from one |
| 6 | entity generation | the sparse index is keyed by **entity index**, so two entities of the same index and different generations never share an entry |
| 7 | OOM rollback | a **one-shot** allocator that recovers after the induced failure, so the assertion after it distinguishes the property from exhaustion (§5.5, `FailingAllocator` does not) |

### 2.8 `@requires`

Variadic (`etch-reference-part3.md` §6). Transitive closure computed once at resolution and
never re-walked per add. A cycle is a resolution error. The whole closure is added in one
transaction or none of it, identically for a spawn carrying a component with a non-empty
closure and for both storage modes. Removing the requirer removes nothing else.

Removal of a still-required component is refused **at type-check wherever the shape of the
program allows the refusal to be static**, and tolerated at runtime with a warning where
static analysis cannot see it. The reason the deferred channel is not available is measured:
the three apply switches of §1.4 return `!void` into a flush whose failure surfaces as a tick
failure no rule can observe.

**Named as a hazard, not resolved here:** the type-checker's static component set is
`RuleCtx.components_in_when` (`types.zig:4298`), computed by `collectWhen` (4651), which
recurses through `.logical_not` **without negating** — so `not has T` still inserts `T`. That
set means *mentioned*, not *carried*, and a static refusal built on it would be wrong in the
negated case. G9 owes that distinction an answer.

## 3. Bounds, and what G0 could not establish

### 3.1 The bound that keeps §1.15 out of scope

Every membership-deciding site outside `src/core/ecs/` — forge's authority routing, its two
change probes, the resources API, the vertical slice, the editor's live-edit apply — is
**correct today and unreachable by a sparse component**, because the mode's only producer is
an Etch annotation and those sites read Zig-declared components.

That bound is load-bearing and it is one field wide: the moment `ComponentDesc` carries a
public defaulted `storage` field, a Zig module can opt in, and every one of those sites
becomes a live defect — several of them silent (`orelse return .solver` flips a semantic;
`orelse return false` reads as *never changed*), several a panic (`.?`).

**This is a design question the brief does not settle: is the mode settable from Zig at all?**
The conservative reading — the annotation is the sole producer, and a Zig-side opt-in is a
separate decision with §1.15 as its cost — is what §2.1 states. It is stated as a contract
clause precisely so that widening it later is a visible act.

### 3.2 What G0 did not establish

- **Whether an Etch-declared empty component (`component X {}`) parses and type-checks
  today.** §1.6 establishes the Zig-side zero-size precedent; the Etch-side shape of the
  spec's own `@storage(sparse) component InCombat {}` example is unexercised in the corpora and
  was not probed, because probing it means compiling a fixture and G0 writes no code. If it is
  refused today, the front-end is in G1's scope for a reason the brief does not name.
- **The C0.1 baseline value.** `bench/ecs_benchmark.zig` gates S1 at *median ≤ 62 µs*
  (ReleaseSafe, 100 000 entities), and `engine-phase-1-plan.md` `M1.D.2` records that gate as
  stale — that row reads the 62 µs gate as expired, M0.8 and M0.9 having measured ~69-91 µs at
  rest. The brief's 5 % is against a
  **baseline**, not that gate. Which number the 5 % is measured against is unresolved and is
  `M1.D.2`'s, not this milestone's; it is named so the closing measurement does not silently
  pick one.
- **The empty-signature case.** §2.3 identifies it; what an entity carrying only sparse
  components is stored as is a decision G2/G3 owes.

### 3.3 A documentary observation, relayed and not acted on

`engine-scene-serialization.md` §4 carries the 2026-09-03 rectification at its head, stating
that the loader does not write column by column and never did. Its own subsection
§4 — *Chargement (loader runtime — M1.0.5)* still lists the six load steps with a **column
memcpy** as the fourth, between the archetype allocation and the UUID remap, and its
pseudo-code copies columns into 16 KB chunks (lines 446, 486-500, 507). `engine-corpus-map.md`
anomaly 88 records that drift as **clos**.

The delivered loader instantiates entity by entity (`loader.zig:387`, single
`spawnDynamicWithValues` at 453), so the head of §4 is right and the subsection is the
superseded version left standing in the same section — a correction upstream leaving its
superseded version standing downstream of its own correction — the sweep pattern of
`engine-development-workflow.md` §5.5, § *Texte et contrats*. It changed no
decision here because the contract was written from the code. Per §3.6.2 this is a
pre-existing drift, recorded for the global audit and **not** patched from a milestone
session.
